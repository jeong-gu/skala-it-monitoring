# 원래 질의 기준의 최종 검증과 보완

정보 조회 성공과 요청 완수를 별도로 관리한다. 계획 모델이 원래 질의의 요구사항을 `requirements`로 기록하고, 모든 조회·답변 생성·검증 단계에 원래 질의와 누적 기록을 전달한다. 최종 검증은 답변 생성에 사용하는 동일한 `deps.quality_llm` 인스턴스를 순차적으로 재사용한다. 현재 개선 평가에서는 `gpt-4o-mini`를 사용한다. 어댑터별 실제 모델은 설정을 따르며, 생성·검토는 같은 일반 모델을 사용한다. 이 모니터링 경로의 최종 검증을 위해 검증용 모델을 별도로 적재하지 않는다.

## 처리 흐름

1. 원래 질의에서 조회·계산·비교·진단·설명 요구를 기록한다.
2. 조회 결과가 부족하거나 실패하면 단계·요구 ID·사유를 `requirement_issues`에 남긴다. 해결된 이력도 삭제하지 않는다.
3. 작성 모델에 원래 질의, 전체 요구사항, 누적 미충족 기록, 실제 근거와 이전 검증 피드백을 전달한다.
4. 대처 요청이면 공식 매뉴얼 근거를 합치고 출력 형식을 정리한 뒤, 실제 최종 본문을 일반 모델이 원래 질의 및 모든 요구사항과 대조한다. 누락된 요구도 추가할 수 있다.
5. 정보 부족은 등록된 정보 ID를 통한 추가 조회로, 계산·설명 부족은 답변 재작성으로 돌아간다.
6. 충족 여부를 다시 검증한다. 미지원·조회 실패·한도 초과·검증 실패를 성공으로 대체하지 않는다.

일반 모델은 답변의 충족/미충족을 판정한다. 정보의 지원 여부는 모델 판정으로 변경하지 않고 프로그램의 실제 조회 상태를 사용한다. 미지원 정보를 확인 불가로 정직하게 설명한 응답은 `partial`이다. 모든 요구를 충족했다고 표시하지 않는다.

## 제한과 보호

- 최초 조회 이후 추가 조회는 전체 과정에서 최대 2회다. 기존 조사 재계획과 최종 답변 보완이 이 한도를 공유한다.
- 명령 결과는 요청당 최대 12건이며 같은 서버·같은 명령을 재조회하지 않는다. 같은 계획의 앞 명령으로 이미 얻은 정보도 재사용한다.
- 최종 답변 보완은 최대 2회, 최종 검토는 최초 포함 최대 3회다. 각 모델 호출의 형식/근거 검증 재시도는 최대 1회다.
- 서버 조사와 대처는 실행 한도를 공유하며, 매뉴얼 검색은 최초 포함 최대 2회다. 관련 없는 성공 단계를 다시 수행하지 않는다.
- `remediation` 요구는 검색된 청크·대응 단계·조건·관측 연결이 있어야 준비 상태가 된다. 모델이 충족이라고 해도 실제 근거가 없으면 거부한다. 일반 매뉴얼 요구만 서버 목록 없이 확인된 OS를 대상으로 기록할 수 있다.
- 최종 형식 정리 뒤의 실제 본문을 검증한다. 통과 뒤 재작성하지 않는다. 형식 정리에 실패한 응답도 완전 충족으로 표시하지 않는다.
- 등록되지 않은 대상, 임의 셸 명령, 외부 서버 연결은 추가하지 않는다.
- 계산은 조회된 숫자 필드를 참조하는 제한된 연산으로 수행한다. `eval`이나 모델이 준 계산값은 실행/신뢰하지 않는다. 결과·피연산자·식·단위·출처를 함께 반환한다.
- 계산 요청에 계산 결과가 없거나, 진단 요청에 검증된 후보가 없으면 일반 모델이 충족이라고 해도 보완 대상으로 처리한다.
- 일반 모델이 요구를 누락하거나 형식/근거 검증을 통과하지 못하면 `unverified`로 반환한다. 이를 자동 성공 처리하지 않는다.
- 원문/JSON 전용 요청은 기존 원문 형식을 유지하고 생성형 답변 검증을 생략한다. 대상 확인/명령 거부 등 조기 종료는 `not_run`이다.

## API와 화면

`/chat`과 SSE `FinalAnswer`에 기존 필드와 함께 다음 필드를 추가한다.

- `requirements`: 고정 ID, 요구 설명, 대상, 필요 정보, 종류, 현재 상태, 변경 이력.
- `requirement_issues`: 중간에 확인한 미충족 사유와 해결 기록.
- `answers`, `calculation_results`: 원문에 근거한 직접 답변과 검증된 계산.
- `final_reviews`: 검증 회차별 판단/피드백 또는 검증 오류.
- `final_validation`: `passed`/`partial`/`unverified`/`not_run`, `request_fully_satisfied`, 검증 모델, 보완 횟수, 사유.

화면의 ‘요청 충족 확인’에서 요구별 상태와 변경 이력을 확인한다. `RequestRequirements`, `FinalAnswerValidation`, `AnswerRepair` SSE 이벤트로 진행 상태를 갱신한다.

## 검증 범위

기존 고정 평가 세트의 기대 답변은 구현 입력·프롬프트·테스트 상수로 사용하지 않는다. 프로토콜 테스트는 모의 모델의 의도적 누락·잘못된 통과·형식 실패·반복 보완·다른 서버 요청을 검증한다. 계산 테스트는 별도의 합성 수치를 변경해 원본 의존성을 확인한다. 고정 평가 세트에서의 성능 개선은 별도의 평가 전까지 주장하지 않는다. 일반 모델의 의미 판단은 완벽하지 않으며 `passed`는 그 실행에서 검증을 통과했다는 뜻이다.


## 요구사항별 보완 상태 유지

설명·계산 보완에는 `verified_results`와 `repair_requirement_ids`를 전달한다. 검증된 새 결과만 해당 요구 ID에 병합하며 다른 요구의 계산·원문 참조·답변을 유지한다. 잘못된 후속 생성으로 기존 결과를 비우지 않는다. 재사용하는 원인 후보는 남겨진 시나리오의 evidence ID와 원문에 대해 다시 검증한다.

현재 의도 분류의 `observation_policy`는 `auto/reuse/refresh/clarify`다. 조회 금지·재사용·새 측정의 자연어 의미는 LLM이 분류하며, 코드에서 정규식으로 그 정책을 덮어쓰지 않는다. 모호하거나 필수 형식 검증에 실패하면 조회하지 않는다. 이전 근거가 없는데 재조회를 금지하면 조회하지 않고 미확인 항목과 조건부 매뉴얼을 제공한다.


## CPU 계산의 집계 기준 검증

시스템 전체 CPU 비율과 프로세스 CPU의 코어 합산 비율은 같은 `%`라도 직접 합계·차이·비율 계산하지 않는다. CPU와 메모리 등 다른 의미의 비율도 혼합하지 않는다. 코어 수나 정규화 기준을 임의로 가정하지 않으며 프로세스 CPU가 100%를 넘는 원문 값 자체는 허용한다.

프로그램이 원본 정보 ID와 필드 경로로 집계 기준을 확인한다. 시스템 CPU 내부의 같은 기준 계산, 정상적인 메모리 단위 환산·페이지 계산은 유지한다. 목록 경로는 음수가 아닌 숫자 인덱스만 허용하여 `entries.-1.cpu_percent` 등으로 기준 검증을 우회하지 못하게 한다. 잘못된 계산은 최종 모델이 충족이라고 판단해도 결과로 승인하지 않는다.


## 2026-10-21 계산 거절과 최종 본문 검증 보완

- 원본 필드에서 확인한 시스템 CPU와 프로세스 CPU의 집계 기준 불일치는 연산·피연산자·원문 참조·안정적인 fingerprint를 포함한 거절 기록으로 유지한다. 동일한 불가능 계산을 일반 정보 부족으로 되돌려 반복하지 않는다. 다른 RSS·페이지 환산 등 유효한 요구의 결과와 근거는 보존한다.
- 피연산자가 원래 요구의 서버·정보 범위를 벗어나면 수정 가능한 잘못된 선택으로 처리한다. 최종 모델이 거절된 연산과 실제 요청의 연결 오류를 명시하면 정상적인 다른 계산으로 보완할 수 있다. 거절된 연산 자체는 승인하지 않는다. 재개방한 수치 비교는 검증된 대체 계산 또는 실제 본문에 남아 있는 원문 검증 답변이 있어야 통과한다.
- 최종 형식 정리 전의 문장 블록에 요구·관측·대응 단계·청크 ID를 연결하고 실제 본문에 남은 블록의 연결만 최종 검증에 전달한다. 수치·계산·출처와 필수 정보에 대한 프로그램 검사를 유지한다.
- 최종 검증 뒤에는 본문을 변경하지 않는다. 한도 소진·검증 실패에 따른 제어 안내는 기존 final_validation·limitations·요구 상태 필드에 기록한다.
- 전체 회귀 185개와 git diff --check를 통과했다. 실제 정확도·속도 비교 및 화면 검증 결과는 프로젝트 밖 langsmith-before-after-v2 산출물에서 별도로 관리하며, 테스트 통과를 실측 성능 향상으로 해석하지 않는다.


## 전문 판단·실패 보존

자연어 분류 모델은 필요한 결과를 조회·계산·비교·진단·설명·대처 유형으로 명시한다.
프로그램은 이 요구를 그대로 조사 원장에 연결한다. 명령을 지정했다는 이유로 계산 요구를 조회로 축소하지 않는다.
계산은 원본 필드와 단위를 참조해 코드로 수행하고, 문장의 수치·인용은 원문과 대조한다.

원인 요청에는 역할별 전문 그래프의 증상 관측 여부를 먼저 반영한다. 정상 상태에서 장애 후보를 강제로 만들지 않는다.
메트릭·로그 중 일부 실패를 다른 역할의 성공으로 대체하지 않으며, 변경 없는 역할의 성공 결과는 재판단·시간 초과 중에도 보존한다.
타이머나 최종 의미 검토 실패 시에는 `unverified`로 반환한다. 이미 검증한 수치·인용이 있다는 사실과 전체 요구가 충족됐다는 판정은 다르다.


## 독립 결과의 보존과 후보 철회

모델 report의 답변·계산·후보는 항목별로 출처를 검증한다. 한 항목의 잘못된 인용이 다른 항목의 유효 계산·설명을 지우지 않도록 검증 직후 저장하고, 재시도 입력에도 전달한다. 미충족 항목은 그대로 남기며 전체 완료로 바꾸지 않는다.

새 판단이 증상 미관측을 뒷받침하면 해당 요구의 이전 후보를 공유 상태에서도 철회한다. 다른 요구 ID는 유지하고, 같은 요구에서 로그 역할이 증상을 관측했다면 정상 메트릭 역할만으로 후보를 없애지 않는다. 검증되지 않은 철회 문장은 적용하지 않는다.

2026-10-22 회귀: 전체 261개 통과. 항목 보존 4개와 철회 경계 3개를 추가했다. 실제 메모리 원인 질의 3회는 내부 검증을 통과했으나, 별도 본문 검토에서 1회는 원인 대신 성능 영향을 설명했다. 내부 passed가 독립적인 의미 정확도를 보장하지 않는다는 한계는 남아 있다.


## 관측 요인 선택으로 원인·영향 혼동 방지

원인 후보를 자유 문장으로 작성한 뒤 문장 유무만 검사하면, 원인 대신 성능 저하라는 영향을 답해도 충족으로 판정할 수 있었다. 현재 report 내부 계약은 `causes[{requirement_id,factor_id}]`로 실제 관측 요인을 선택한다. 프로그램이 이를 기존 공개 `hypotheses` 형식의 조건부 기여 후보로 렌더링한다. API 응답 필드는 유지한다.

- 후보 카탈로그는 원문을 다시 파싱한다. 프로세스 CPU(코어 합산)·메모리 점유율/RSS, 등록된 로그 디렉터리 사용량, 로그에 명시적으로 기록된 `reason=`을 다룬다. 집계 사용률이나 오류 키워드 자체를 원인으로 만들지 않는다.
- 모델이 관련 주요 후보를 선택한다. 같은 요구·서버·요인 종류에서는 하나를 선택하고, 서로 다른 종류·요구는 보존한다. 후보 자체는 원인의 확정이나 주된 원인에 대한 증명이 아니다.
- 증상과 요인 양쪽의 근거가 필요하다. `top`에 CPU·메모리가 함께 있어도 실제 인용 행의 주제가 일치해야 한다. CPU load 행만으로 CPU 사용률의 증상을 승인하지 않는다.
- 로그 저장량은 가장 긴 일치 mount에 연결한다. 다른 정상 파일시스템의 로그를 가득 찬 root의 원인으로 제시하지 않는다. 기존 디스크 압박 검사와 같은 사용률90% 기준을 사용하므로, 별도 임계값이나 다른 용량 기준의 진단에는 한계가 있다.
- 후보가 없는 진단을 완료로 인정하는 예외는 검증된 `symptom_observed=false` 설명이다. 판정 생략이나 영향 설명만으로 이를 대신할 수 없다. 관측·원인 후보 부족은 partial로 남긴다.
- 원인 후보 재작성 실패 시에도 이미 검증한 계산·설명·증상 판단을 보존한다. 정상 재판정은 과거 후보를 철회한다. 기존 추가 조회·모델 수정 한도는 유지한다.

검증: 원인 대신 영향, 판정 생략, 다른 서버·다른 지표, 정상 증상, 다중 행 df/log, CPU load-only, 후보 철회와 부분 결과 보존 등을 포함한 전체276개 테스트가 통과했다. 단위·모의 통합 테스트 통과는 실모델 전체 정확도 보증이 아니다.

실제 GPT-4o-mini 개발 검증 v2에서는 메모리3회(93.75% 계산+cache-worker 기여 후보), 높은 CPU(시스템96%와 프로세스372% 기준 분리), 정상CPU19%(후보 없음)가 독립 내용 검토를 통과했다. 디스크는 df 이후 로그 저장량으로 이어지지 않아 partial이었다. 해당6회 기록은 마지막 다중 행 인용 수정 이전 소스이며, 최신 최종 비교평가나 화면 검증을 대체하지 않는다. 메모리 본문의 중복 설명과 성공 후 내부 후보 거절 횟수 노출도 남아 있다.


## 디스크 진단에서 로그 전문 역할로 추가 조사 연결

디스크 사용률만으로 공간을 차지하는 요인을 설명하지 않는다. 메트릭 역할이 실제 파일시스템 행을 인용해 공간 압박을 판단하면, supervisor가 등록된 `/var/log/`의 가장 긴 일치 mount를 확인한다. 그 mount가 기존 압박 기준인 사용률90% 이상인 경우에만 로그 전문 역할에 `log.usage` 지원 조사를 배정한다. 별도의 정상 로그 파일시스템을 가득 찬 root의 원인으로 연결하지 않는다.

지원 배정에는 원래 요구 ID와 대상이 유지된다. 사용자 요구 목록에 새로운 로그 요구를 만들지 않는다. 로그 역할은 디스크 관측을 읽기 전용 맥락으로 볼 수 있지만 조회 권한은 `log.*`에 한정된다. 동일한 collection callback이 추가 조회2회·명령12건·중복 조회 금지·재사용 정책을 적용한다.

지원 설명은 원문에서 파싱한 로그 저장량과 별도로 요청한 로그의 발췌로 구성한다. 자유 문장으로 집계 사용률 자체를 원인으로 바꾸지 못하게 하며, 조건부 원인 후보는 기존 관측 요인 선택 계약으로 작성한다. 조회가 실패하면 이미 확보한 디스크 결과를 유지하고 partial로 남긴다. 변경 없는 지원 결과도 재평가 시간 초과 전에 복원한다.

정상 디스크 판단은 자연어 부정 표현으로 판정하지 않는다. disk-only 판단의 `symptom_observed=false`와 실제 df의 모든 관련 행·대상·인용을 함께 확인하고, 관측 수치와 미관측 전제를 프로그램이 서술한다. 사용률90% 이상인 행을 false 플래그로 정상 처리할 수 없다. 이미 역할별 검증을 통과한 로그 지원 판단을 원래 disk 요구로 다시 해석하지 않는다.

한계: 현재 지원 경로는 등록된 `/var/log/`의 저장량이다. 다른 디렉터리·삭제된 열린 파일·inode·시계열·실제 로그 순환 설정은 이 관측으로 확인되지 않는다. 사용률90%는 기존 보수적 검사와 일치시키는 기준이며 서비스별 임계값 설정을 대체하지 않는다. 후보를 주원인이나 확정 원인으로 표현하지 않는다.

검증은 정상/압박, 별도 mount, 원문·대상 불일치, 로그 조회 실패, 보완 중 재사용·시간 초과, 공유 한도, 역할별 판단, 증상과 원인 혼동을 포함한다. 실제 GPT 개발 실행은 실패 시도까지 별도로 보관한다. 단위 테스트와 개발 질문 몇 건의 통과를 전체 서비스 정확도 또는 최신 Before/After 성능으로 해석하지 않는다.

### 2026-10-22 수치와 지표 연결 보완

원문에 등장한 숫자 집합만으로 답변을 허용하던 검사에, 명시적 CPU 하위 지표·프로세스별 CPU/메모리/RSS·메모리 용량 필드의 연결 검사를 추가했다. 저장된 facts만 믿지 않고 원문을 다시 파싱한다. 다른 지표의 숫자나 계산 결과가 존재한다는 이유로 CPU 사용률을 바꾸어 인용할 수 없다. CPU18·다른 값40을 CPU40으로 답하는 재현, 프로세스 사이 값 교환, 메모리 total/used/available 교환, 원문과 facts 불일치, 정상 영문 하위 지표 표현을 테스트한다.

이 검사는 명시적 지표·단위 표현을 보강하는 결정론 검사다. 자유문장 전체의 의미를 보증하지 않으며 기존 최종 의미 검증과 계산 피연산자 검증을 대체하지 않는다. 추가 조회나 모델 호출은 발생시키지 않는다. 기존 재시도 한도를 유지한다.
