# 공식 매뉴얼 기반 대처방안 RAG

대처·조치·대응·해결 방법을 요청했을 때만 실행한다. 상태 조회, JSON/원문 전용 요청에는 RAG를 호출하지 않는다.
Linux와 macOS의 CPU·메모리·디스크를 지원한다. 별도 원문 페이지나 조치 실행 기능은 없다.

## 로컬 구성

- `data/manuals/originals`: 공식 사이트에서 받은 HTML·roff 원본 6종.
- `data/manuals/text`: 탐색 메뉴를 제외하고 추출한 영문 본문.
- `data/manuals/manifest.json`, `chunks.json`: 출처·OS·제품/버전·수집일·SHA-256·절·장애 유형·BGE 토큰 수.
- `data/manuals/retrieval.json`: 개발 질문만으로 보정한 OS별 코사인 유사도 기준.
- `data/manual_index`: 로컬 Chroma 파생 데이터. Git 제외. 삭제 시 다시 색인한다.
- `.manual_cache`: 수집 단계의 BGE 토크나이저. Git 제외.

Linux 커널 cgroup v2 CPU·메모리 제어 절, logrotate, Apple 성능 저하·저장 공간 확보·프로세스 종료 문서를 사용한다. 조회 명령 사용법은 조사 코드가 관리하므로 RAG에 넣지 않는다.
모든 원본은 출처 URL과 해시를 보관한다. `source snapshot` 버전은 특정 제품 버전을 확인했다는 뜻이 아니라 수집 시점의 원본을 고정했다는 뜻이다.
기존 `data/runbooks`의 교육용 문서는 이 인덱스에 포함하지 않는다.

## 준비와 갱신

프로젝트 가상환경에서:

```bash
uv pip install --python .venv/bin/python -r requirements.txt
ollama pull bge-m3
.venv/bin/python -m remediation.collect
.venv/bin/python -m remediation.index --build
.venv/bin/python -m remediation.evaluate --calibrate --output /tmp/manual-calibration.json
```

원문을 갱신할 때는 `remediation.collect --refresh` 후 색인·개발 평가를 다시 수행한다.
수집 명령은 네트워크를 사용하지만 채팅 중에는 공식 사이트에 접속하지 않는다.
색인은 원본·모델·청크 변경을 비교하고 달라진 텍스트만 임베딩한다. 새 컬렉션을 완성한 후 활성 포인터를 교체한다.
임베딩 모델을 바꾸면 재색인과 재보정이 필요하다. 이전 인덱스에 새 모델 질의를 섞지 않는다.

환경 변수:

- `MANUAL_EMBED_MODEL`: 기본 `bge-m3`.
- `MANUAL_OLLAMA_URL`: 기본 `http://127.0.0.1:11434`. 로컬 HTTP만 허용.
- `MANUAL_INDEX_DIR`: 기본 프로젝트의 `data/manual_index`.

## 처리와 정확도

1. 요청 의도를 확인하고 등록 서버 또는 명시된 OS를 사용한다. OS가 없으면 확인한다.
2. 특정 서버의 대처 요청은 같은 세션의 해당 서버 관측을 재사용하고, 이전 관측이 없거나 새 조회를 요청하면 먼저 조사한다. 일반 OS별 매뉴얼 질문은 서버 조회 없이 처리한다. 조회 실패 시에는 실패를 명시한 조건부 안내와 부분 완료 상태를 제공한다.
3. MCP `search_remediation_manuals(query, os, evidence_summary)`로 로컬 의미 검색을 수행한다.
   검색 임베딩은 현재 질문을 기준으로 한다. 혼합된 지표 수치가 검색 주제를 바꾸지 않도록 이전 관측은 대응 단계의 적용 여부를 판단할 때 사용한다.
4. OS·이식 가능한 적용 범위·검토된 대응 단계가 있는 원문 구간으로 후보를 제한한다. 상위 5개 후보에서 점수·중복 검사를 거쳐 검색 1회당 최대 2개 구간을 반환한다.
5. 모델이 검색 결과에서 요청한 장애 유형들과 원문에 연결된 대응 단계 ID를 선택한다. 복합 요청은 문제별 요구 ID와 관측 ID를 연결한다. 이미 수행한 진단을 새 조치로 반복하지 않으며, 프로그램이 검토된 한국어 요약문·조건·출처를 출력한다.

한국어 기술 용어는 영문 검색어를 보완한다. 이것은 incident_type을 키워드로 결정하는 분류기가 아니다.
장애 유형은 검색된 문서와 대응 단계의 메타데이터에서 선택한다.
한국어 요약은 원문의 문장과 대조한 응답용 주석이며, 번역본을 원문으로 저장하거나 임베딩하지 않는다.
새 매뉴얼을 추가하면 해당 원문에 연결된 한국어 단계 주석도 검토해야 한다.

모델은 자유로운 조치 문장·명령·수치를 작성하지 않는다. 반환된 ID, 원문 인용, OS, 장애 유형을 검사한다.
단독 검색 도구는 검색 1회이며, 통합 요청은 필요한 경우 추가 검색 1회를 허용해 총 2회로 제한한다. 같은 검색은 캐시를 재사용한다. 각 요약 생성의 형식·근거 수정은 최대 1회이고, 전체 답변 보완은 최대 2회다.
적용 가능한 실제 조치만 1–5개 선택한다. 한 단계만 있어도 유효하며 최소 개수를 채우기 위한 조회·불필요한 조치를 추가하지 않는다.
재시작·종료·삭제·설정 변경은 실제로 실행하지 않는다. 권장 절차와 실제 관측을 구분하고 영향·전제조건을 표시한다.
Linux 자원 제어는 cgroup v2·컨트롤러·대상 작업·권한을 확인한 경우에만 검토할 조건부 완화책이다. CPU 제한은 지연·처리량에 영향을 주고 memory.high는 회수 압박·지연을 만들 수 있다. 메모리 부족의 원인을 해결하거나 즉시 여유 공간이 생긴다고 보장하지 않는다.

`/chat`과 SSE `FinalAnswer`에 선택적 `remediation`이 추가된다.
status는 `provided`, `not_found`, `needs_clarification`, `unavailable`이며 steps·sources·unconfirmed·timings_ms를 포함한다.
인덱스·임베딩·요약 실패는 별도 상태로 알리고 확보한 서버 evidence는 유지한다.
조사 재사용 정보는 기존 SQLite의 별도 `investigation_context` 테이블에 세션별로 저장한다. 기존 메시지 스키마는 바꾸지 않는다.

임계값은 개발 세트만으로 결정한다. 최종 질문을 반복 실행한 뒤에는 미관측 일반화 성능으로 해석하지 않는다.
정답 문서 포함 여부뿐 아니라 각 단계의 OS·원문 연결·장애 유형도 확인한다.
임베딩·검색·요약 시간을 구분하고, 단일 실행 시간을 평균 성능이나 개선율로 표현하지 않는다.


## 시나리오 선택과 대처 범위 검증

프론트는 `/monitoring/scenarios`의 공개 목록에서 하나를 선택하고 `scenario_id`를 전달한다. 선택 시나리오는 요청별 상태이며 Agent에 시나리오 정답 라벨을 전달하지 않는다. 같은 대화 ID도 시나리오별로 이력·관측을 분리하며 전환 시 화면은 새 대화를 시작한다.

대처 요구는 비어 있지 않은 지원 정보 ID(CPU·메모리·디스크 및 디스크 진단용 로그 파일/저장량)와 출처 주제가 연결돼야 한다. 네트워크·프로세스·로그 내용만의 대처 또는 미분류 요구는 무관한 CPU 문서로 충족 처리하지 않는다. 복합 요청의 지원되는 단계는 유지하고 미지원 요구 ID를 `unsupported_requirements`에 남겨 전체 `partial`로 반환한다.


## 2026-10-21 검색 개수 정책

- 후보 5개, 최종 반환 최대 2개는 검색 1회 기준이다. 후보가 5개 미만인 인덱스에서는 존재하는 수만 요청한다.
- 여러 Task와 추가 검색에서 모인 서로 다른 청크에는 별도의 누적 개수 상한을 적용하지 않는다. 청크 ID로 중복을 제거한다. 검색 두 번에서 서로 다른 청크 4개를 유지하는 통합 회귀 사례를 포함한다.
- 요청 전체 검색 최대 2회와 요약 최대 5단계, OS·원문 해시·인용·요구 연결 검증은 유지한다. 반환 개수 변경만으로 문서를 다시 임베딩하지 않는다.
- `retrieval.json`의 `result_chunk_limit=2`는 검색 결과 한도를 기록한다. 이전 `summary_chunk_limit=3` 메타데이터는 제거했다. 기존 개발 기준과 인덱스는 유지하고 검색 평가를 다시 실행한다.


## 2026-10-21 요구별 대처 근거와 본문 연결

대응 단계마다 해당 주제·전제조건·공식 문서 제목·절을 함께 표시한다. 요구 ID와 관련 관측·청크 연결을 유지하며, 최종 형식 정리 뒤 실제 본문에 단계·조건·출처가 남았는지 확인한다. 유효한 메타데이터만 있고 본문에서 누락된 절차를 충족으로 처리하지 않는다. 단계의 내용·조건·위험도·주제는 같은 원본 청크의 등록된 대응 후보와 대조한다.

같은 본문·근거·미충족 이유가 반복되고 새 조사도 필요하지 않은 대처 요구는 한도까지 같은 보완을 반복하지 않고 미충족 기록을 유지해 종료한다. 진단 등 다른 요구의 보완 기회를 이 규칙으로 줄이지 않는다. 요청당 검색 최대 2회, 검색당 최종 청크 최대 2개와 누적 청크 중복 제거 정책은 바꾸지 않았다.


## 매뉴얼 전문 에이전트와 부분 결과 보존

`agent/remediation.py`의 `ManualAgentState`와 `build_manual_agent()`는 독립 compiled subgraph다.
Supervisor가 대처 요구를 배정하면 `retrieve → assess → retrieve`로 움직인다. 선택 모델은 검색된 근거의 절차만 선택한다.
배정된 정보 ID에 대응하는 주제가 검색 결과 메타데이터에 없으면 해당 요구로 검색을 좁혀 한 번 더 조회한다.
모델에 없는 원문을 만들어내도록 요구하지 않는다. 검색 도구만 주입하므로 이 역할은 서버 명령을 조회하거나 실행할 수 없다.
요청 전체의 검색 2회 제한과 동일 질의 캐시는 재보완 중에도 유지한다. 누적 청크에는 추가 전역 상한을 두지 않는다.

각 선택 이후 원문·요구 연결이 확인된 단계와 출처를 저장한다. 두 번째 검색·선택이 실패하거나 시간 제한에 도달해도 먼저 검증한 결과를 유지한다.
재보완 시작 시에도 기존 검증 결과를 첫 이벤트 전에 복원한다. 일부 단계 제공은 전체 요구 충족과 다르며, 누락 요구는 `partial`, 시간 제한은 `unverified`로 남긴다.
`SpecialistDelegated`, `SpecialistAssessed`, `SpecialistReturned`/`SpecialistFailed` 이벤트로 역할 진행 상태를 전달한다.

2026-10-22 검증: 전체 회귀 254개 통과. 매뉴얼 전문 역할 관련 8개 회귀에는 복합 주제, 두 번째 검색/선택 실패, 손상된 출처, 공유 검색 한도, 첫 실행 및 재보완 중 시간 제한을 포함한다.
실제 GPT-4o-mini + MCP stdio + 로컬 HTTP 시나리오 + BGE/Chroma 개발 실행에서 Linux CPU·디스크, macOS 메모리, Linux 복합 주제 4건이 내부 최종 검증을 통과했다.
이는 단회 개발 확인이며 미관측 정확도, 화면 검증, 최신 Before/After 개선 입증을 대체하지 않는다.

기존 `remediation.evaluate` 명령은 검색/매뉴얼 컴포넌트 평가다. 비호출 사례는 legacy 정규식 경로를 사용하고, 모델 평가는 매뉴얼 노드를 직접 호출하므로 현재 `/chat` 전체 경로의 통합 평가로 제시하지 않는다.

## 2026-10-22 해결 절차 전용 정리

RHEL 조회 도구 개요·메모리 진단, GNU df·du 사용법, Apple CPU·메모리 조회 문서 6종을 제거했다. 원본·추출 본문·manifest·chunks·활성 벡터 색인을 함께 갱신한다. 수집기는 등록된 실제 조치가 있는 구간만 색인하며, 이전 manifest에서 제외된 문서의 파일만 지운다. 전체 공식 원본은 남긴 조치의 검증용으로 보관한다.

검색은 상위 5개 후보에서 중복을 제거해 최대 2개를 반환한다. 첫 문서의 주제를 정답으로 가정해 다른 후보를 버리지 않으며, 조치 선택 모델이 요청·관측·적용 조건에 따라 실제 사용 여부를 판단한다. 사용하지 않는 앱 종료, 파일 이동·압축, 로그 순환, 조건부 자원 제어가 대응 대상이며 지표 조회 방법은 대응 목록에 없다.

새 색인 생성이 성공한 뒤 이전 official 컬렉션을 제거한다. 정리가 중단되면 같은 인덱스로 다시 빌드해도 정리를 재시도한다. 다른 이름의 사용자 컬렉션은 유지한다. 이전 평가 결과는 변경 전 데이터 기준이며 검색 기준을 다시 보정해야 한다.

색인 임베딩에는 영문 원문과 기존 장애 유형 메타데이터를 함께 사용한다. 예를 들어 logrotate에 등록된 `disk-full`을 검색 문맥에 포함한다. 원문·인용은 변경하지 않으며 사용자 키워드로 장애 유형을 확정하지 않는다.

통합 검색에는 이미 LLM이 분류한 정보 ID의 의미(CPU 부하, RAM 압박, 디스크 부족)를 영문 주제로 전달한다. “그 상태”나 목적어가 생략된 요청도 원래 주제를 잃지 않는다. 첫 검색에서 조치 선택이 실패했더라도 누락된 주제가 있으면 남은 검색 1회를 사용할 수 있으며 전체 검색 2회 한도는 그대로다.
