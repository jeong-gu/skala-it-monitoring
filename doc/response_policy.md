# 요청별 도구 판단과 최종 출력

- 이전 대화 없이도 OS와 증상이 있는 대처 요청은 공식 매뉴얼 RAG를 사용한다. 이전 관측은 선택적인 추가 근거다. OS가 없으면 먼저 확인한다.
- 모니터링 용어가 있는 것과 관측이 필요한 것은 다르다. 일반 모델이 개념 설명·서버 관측·매뉴얼 대응·기존 인시던트를 구분한다. 개념 설명은 MCP 호출 없이 답한다. 실제 서버 값은 간단한 질문이어도 조회한다.
- 원문/JSON 전용 요청은 기존 결과를 그대로 반환하고 의도 분류·최종 출력 생성 모델을 생략한다.
- 최종 출력은 기존 일반 모델을 재사용한다. 간단한 task는 1–2줄이다. 복잡한 task는 배경·원인·근거·대처·조건·한계 등 필요한 항목을 나누고 마지막에 3–4줄 요약을 둔다.
- 조사·RAG 경로에서는 LLM이 검증된 내용 블록의 배치와 요약 근거를 선택한다. 숫자·명령·문장을 새로 생성하지 못한다. 본문 누락, 근거 ID 조작, 사실/원인/미확인 구분 변경을 거부하고 수정은 최대 1회다. 실패 시 기존 검증된 본문과 `presentation.status=fallback`을 유지한다.
- `/chat`, SSE `FinalAnswer`에 `presentation`을 반환한다. 최종 형식 정리가 끝난 답변만 채팅 본문으로 표시한다. 기존 인시던트 작성 단계의 토큰은 `DraftToken`으로 구분한다.
- 최종 출력 단계는 기존 조사 요구사항 검증·추가 조회 한도를 대체하지 않는다. 자유로운 재서술 대신 검증된 원문 블록을 사용해 기존 검증 결과를 보존한다.

## 조사·공식 매뉴얼·전체 검증 통합

특정 서버의 대처 요청은 `investigate_remediate` 경로에서 처리한다. 요청 분류 모델이 선택한 정보 ID를 초기 Task에 재사용하고, 필요 정보 조사 → 공식 매뉴얼 → 최종 형식 정리 → 실제 출력문 전체 검증 순서로 실행한다. 단순 상태·대처 요청을 원인 조사로 확대하지 않으며, 원인 요청이 있을 때만 추가 조사와 후보 해석을 수행한다.

서버 한 대를 지원하며, 여러 서버의 대처 요청은 명령 결과 조회 전에 확인한다. 같은 세션·대상의 관측을 재사용하되 '다시/새로/지금/최신' 조회 요청은 새로 확인한다. 여러 문제의 대처는 요구사항을 분리하고 출처·관측을 각각 연결한다. OS가 명시된 일반 매뉴얼 질문에는 서버 조회를 추가하지 않는다.

요구사항·미충족 이력·관측 ID·명령 시도 목록·실행 횟수는 요청 전체에서 유지한다. 최초 조사 후 추가 조사 2회, 명령 12건, 매뉴얼 검색 2회, 답변 보완 2회, 전체 검증 3회다. 각 모델 형식·근거 재시도는 1회다. 추가 매뉴얼 검색은 누락된 대처 주제나 새 문제가 확인된 경우에만 수행하며 기존 자료를 재사용한다.

명시한 명령이 없는 정보 조회에서는 더 많은 미확보 항목을 제공하는 명령부터 처리한다. CPU와 메모리를 함께 요구하면 계획의 정보 순서에 관계없이 top의 결과를 공유하고, 확보된 메모리를 free로 반복 조회하지 않는다. 사용자가 명령을 직접 지정한 경우에는 지정한 명령을 유지한다.

조사와 매뉴얼 생성을 완료한 실제 출력문을 동일한 일반 모델로 검증한다. 통과 뒤에는 본문을 다시 생성하지 않는다. 대응 단계의 `requirement_ids`, `evidence_ids`, 기존 `chunk_id`를 확인하고 코드가 출처 무결성·주제 일치를 검사한다. 조회된 진단을 대응 단계에 반복하지 않는다. 조회 없이 안내한 서버 대처는 `conditional`로 구분한다.

조회 실패 시 OS·증상이 분명하면 조건부 매뉴얼을 제공하고 `partial`로 반환한다. 매뉴얼 실패 시 관측 결과를 유지한다. 필수 근거 부재·미지원·한도 소진은 성공으로 대체하지 않고, 검증 자체가 실패하면 `unverified`다. 출력 형식 정리 실패도 완전 충족으로 표시하지 않는다.

`/chat`과 SSE에는 기존 필드와 함께 `workflow_budget`, `workflow_timings_ms`를 제공한다. 시간은 단계별 누적 경과 시간이며 `total`은 통합 조사 함수의 경과 시간으로, HTTP 전체 시간과 구분한다. 실제 운영 서버 연결·명령 실행 기능은 추가하지 않는다.

## 요구 계약

- A·B 등은 동시 조사할 운영 서버가 아니라 사용자가 하나씩 선택하는 테스트 시나리오다.
- 선택 시나리오 ID는 POST /chat 및 GET /chat/stream에 선택적으로 전달한다. 기존 ID 없는 클라이언트는 호환한다.
- 선택 변경 시 프론트는 새 thread_id와 빈 화면을 사용한다. API는 같은 thread_id라도 시나리오가 다르면 이력·관측을 분리한다.
- 선택 시나리오와 질문의 명시 대상이 충돌하면 조회 전에 안내한다. 서로 다른 시나리오의 후보·근거를 혼합하지 않는다.
- CPU·메모리·디스크 밖 또는 주제가 정해지지 않은 대처 요구를 무관한 매뉴얼로 충족 처리하지 않는다. 복합 요청은 지원되는 부분의 근거를 보존한다.
- 설명 보완 시 검증된 계산·답변을 요구사항 ID별로 유지하고, 보완 대상만 교체한다. 생성 실패도 기존 검증 결과를 지우지 않는다.
- 기존 intent 호출에서 observation_policy=auto/reuse/refresh를 판단한다. 명시적 재조회 금지는 코드에서도 우선하며, 다시 설명과 새로 측정을 구분한다.

## Global Constraints

- "파일 이동·이름 변경·새 디렉터리 생성 없이 기존 파일을 수정한다."

- "실제 서버 연결·셸 실행·자동 조치는 추가하지 않는다."
- 추가 조사 최대 2회, 명령 결과 총 12건, 매뉴얼 검색 최대 2회, 답변 보완 2회·전체 검증 3회, 호출별 형식·근거 재시도 최대 1회.

### 동일 입력 비교에서 발견한 의도 분류 경계 보완

CPU 조회와 메모리 비율 계산을 한 문장으로 요청하면 모델이 공통 서술어를 붙여 원문 인용을 재작성하는 사례가 있었다. 의미 분류가 맞아도 실제 원문에 없는 인용이므로 그대로 승인하지 않는다. 원문 인용 오류에 한해서, 재시도 스키마에 원문의 연속 부분 구간 후보를 제시한다. 이미 유효한 인용과 400자 이내의 전체 요청도 후보로 유지한다. 후보 선택과 결과 종류·정보 ID 판단은 모델이 수행하며, 코드가 분류 결과를 자동 승인하거나 요구를 삭제하지 않는다. 같은 상태의 인접 관측 재사용 이외의 과거 질문은 후보에 포함하지 않는다. 기존 최대 2회 분류와 최종 원문 일치 검사는 유지한다.

`route=chat`인데 기본 상태 조회 또는 관측·대처 요구가 동시에 있으면 모순된 계약이다. 이때 관측 목록을 우선하여 자동으로 명령 경로로 승격하지 않고 모델에 일관된 분류를 다시 요청한다. 재시도도 모순이면 도구 없이 확인 응답으로 종료한다. 선택된 시나리오나 정보 카탈로그의 존재 자체를 조회 요청으로 간주하지 않는다.

### 진단 후보 누락 검증 (2026-10-22)

전문 에이전트의 증상 판단과 별도의 설명 답변만으로 원인 조사 요구를 완료하지 않는다. `eligible_cause_choices`는 기존 `bind_cause`의 대상·주제·원문 검증을 통과한 후보 쌍만 제시하며, 후보 선택은 모델이 수행한다. 작성 결과에서 해당 요구의 후보가 빠지면 최종 검증에 앞서 기존 1회 재시도 범위에서 보완한다. 재시도 중 이미 검증된 설명·계산·다른 요구의 후보는 보존한다.

### 복합 조사·해결 요청과 전문 판단 계약 보완
